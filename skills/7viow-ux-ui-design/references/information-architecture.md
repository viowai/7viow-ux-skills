# Information architecture for the actual task

Read the relevant branch when creating or materially changing content organization, navigation or finding paths. A local visual repair stays within its selected structure. Express decisions in the artifact or existing specification; do not produce a document for every method name.

## Tasks, objects and affected content

Identify the user's goal, trigger, necessary input, consequential decisions, actions, completion and recovery. Decompose the steps where understanding or action can fail, not every mouse movement. Use actual research when available; otherwise name assumptions about user understanding rather than claiming a validated mental model.

For migration or substantial content reorganization, inventory the affected objects: stable identity, purpose, source, relationships, audience, useful fields and duplicate/outdated/missing content. Cover the full set when the request promises full coverage. Otherwise bound the inventory to the changed task. Preserve decision-critical missing information as unknown; omit empty optional metadata from the reading surface.

Reuse one content model for labels, menus, search, detail and exports. Separate the object's identity from its current menu position or display name. A taxonomy change need not be a database or platform redesign. Completion: the content supporting the task has an owner and a traceable destination, with meaningful omissions explained.

## Choose an organizing pattern

Compare plausible task-, object-, time-, hierarchy- or facet-based organization against what the user needs to find, understand or decide. Use a hierarchy for stable containment, a flow for decisions and state transitions, and facets for intersecting properties. Neither a tree nor a card grid fits every collection. For undecided substantial structure, use the existing direction-selection process with inspectable alternatives.

Map only the relationships needed for the decision. A site map shows page/content structure and cross-links; a task flow shows sequence, branches and recovery. They may share one model without becoming duplicate deliverables. For multiple roles/systems/channels, show who supplies information, who decides, where the task passes across a boundary and how it returns after failure. A single-screen repair does not require an ecosystem map.

Completion: the chosen pattern supports a representative real task and its important exception; the structure can be judged in a visible keyframe, not only in labels on a diagram.

## Navigation and reachability

Give global, local, contextual and utility navigation distinct jobs where needed. Show current location, a useful next step and a way to return with appropriate context. A deep link, search result, related-content link or role-specific entry may be a legitimate primary entrance; not every page belongs in the main menu. Avoid dead ends in the promised task.

Keep long-content reading usable: meaningful headings, relevant jumps, source links near the claim and a return path. On narrow screens, preserve information priorities and reachable actions instead of merely stacking desktop panels. Changes to a label or classification must preserve promised URLs, context and source identity, or explain an intentional migration.

Completion: entry → find → understand/act → return/recover works for the intended reader, including the changed narrow-screen path.

## Labels, metadata and search

When ambiguous vocabulary, synonyms or localization affect retrieval, use a small concept table: identity, preferred label, aliases and context. Add broader/narrower/related terms only if the finding task needs them. Read ux-writing.md for wording; keep states distinguishable instead of replacing them with emotional synonyms.

Define only metadata with a consumer: meaning, allowed/missing values, visibility and its role in search, filters, sorting or status. Engineering owns storage schemas and retrieval implementation. Use interaction-contracts.md for query/facet combinations, counts, ranking, zero-result recovery and detail/return. Test with terms a reader would know, including an alias or an ambiguous query when relevant.

Completion: a real query and a meaningful facet combination lead to the intended object with an understandable label and scope. A full thesaurus, ontology or new search feature is not required without a corresponding task.

## Evidence, iteration and specialist boundaries

Choose evidence that can settle the design question. Expert walkthrough, tree-testing plans, observed participant paths and live analytics establish different things. Participant research needs actual participants, consent, tasks and an appropriate environment; do not invent success rates or predict completion times from a theoretical model.

Use supplied logs only after checking event meaning, time window, denominator and segmentation. Treat behavior as a hypothesis source, not a direct measure of satisfaction. Revise the classification, label or path implicated by evidence, then retest that task and adjacent paths; do not rebuild the entire IA after every finding.

Cross-channel work preserves object, state, terminology and continuation while allowing different interfaces. Formal cognitive models, knowledge graphs, semantic retrieval, spatial/ambient interfaces and commercial ranking require appropriate specialist inputs and tools. Define the user's problem and observable UX result, then hand the specialist its bounded question. Do not silently start a new technical system or claim that an unavailable specialist outcome is complete.
