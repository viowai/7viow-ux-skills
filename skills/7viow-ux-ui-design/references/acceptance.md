# Task acceptance

Use for the final self-check of generated/modified artifacts. Select checks that can detect a concrete failure in the affected task.

1. Open the actual deliverable. Verify its resources and main task in the intended runtime. Source syntax and a file path do not prove the rendered result.
2. Execute entry → decision → action → feedback → return/recovery. Compare content identity, status, units, and time scope with supplied facts. Verify each promised interaction rather than counting buttons.
3. Inspect representative desktop and narrow views, real long content, empty results, and short height when relevant. Check reading order, text/labels, reachable actions, overlap, focus, and useful visual hierarchy as well as overflow.
4. Test persistence/recovery where promised: drafts, close/back, refresh, selection, and export/import. Use isolated test data; inspect the exported result. Restore temporary state after testing.
5. For modifications, retain the original source/decisions and compare affected behavior with the baseline. If outputs are generated, follow source-repair.md and check the regenerated artifact plus another affected record/state; distinguish source changes, build success, and observed task success. Check likely adjacent regressions; broad unrelated tests are not a substitute for the task result.
6. Inspect the actual images or rendering when judging visual craft. A DOM measurement can identify clipping but cannot by itself establish a polished visual result. An automated pass and a visual review should say what each covered.

For UI copy changes, inspect the per-item counts/budgets and individually justified exceptions from ux-writing.md; check factual meaning separately.

Record action, expected, actual, artifact/version and evidence. Separate passed, failed, and not tested. When evidence tools are unavailable, finish authorized work and identify the remaining verification gap rather than calling it a completed interactive acceptance.

Use a short review guide with the actual output entrance. Keep internal check files separate from the user-facing product. Independent evaluation requires a fresh executor without the author's expected answer or intervention; ordinary self-checks are not proof of generalization.

## Actual delivery medium

For each promised format, inspect the version saved/imported in its intended application and its actual export. Track native structure/editability, readable output, links and applicable interactions separately. Another renderer's preview proves only that renderer's result. Cover the formats and paths this request changes; do not turn a single-format task into a universal export exercise.

Before repeating a visual pattern across many pages, inspect a representative difficult page with real content at the intended viewing scale. Check relationships, hierarchy and decision-critical conditions. A technically valid file, a fitting text box or a passed script cannot override a content or visual failure.
